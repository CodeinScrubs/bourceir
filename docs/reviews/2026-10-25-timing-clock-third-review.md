## R1: timing and architecture claims

| Claim | Adjudication |
| --- | --- |
| P1: 9.9773 ms proves a severe regression caused by repeated Layout/DPI reads | Unsupported causal conclusion. The number is a real adjacent native-boundary sample in one of three trials. Previous 2.1.1 send-start measurements were pre-commit gate samples, so treating them as equivalent native-entry measurements is invalid. Workload/cold-path effects were not controlled; a maximum of three samples is not a worst case or performance comparison. Guard duration and full-precision boundaries are now retained in the fixture rows. Added checks do work; their individual timing cost still needs measurement. |
| P1 fix: expected snapshot replaces the current capture's first pass, so drop the second pass without weakening guards | Rejected. The expected snapshot may be minutes old. One sequential fresh sweep can mix fields from different moments; comparing it with old expected values does not replace an intra-capture consistency reread. Full stability checks remain, with a final active-desktop reread and a short additional near-input check. If a selected 5 ms tolerance is exceeded, rejection is its intended contract, not evidence that a timing-valid click was wrongly aborted. |
| P2: picker minimization can affect focus, hides countdown, and can fail on small screens | Valid usability limits. They are documented. This is not a guarantee for focus-sensitive menus/popups. Success restores a non-covering normal window; a previously maximized window can intentionally return windowed. No possible non-covering placement means rejection. The owned physical fixture exercises the visible/topmost workflow. |
| P2 fix: temporarily transparent/layered window, restore opacity in place, selection never fails | Not accepted as a drop-in fix. Layered hit testing is not the same as a durable unobscured destination. Restoring the clock over the point can make the final guard reject or change the visual/action context. It does not solve the post-capture obstruction. No promise that selection can never fail is appropriate. |
| P3: notification races consumption; add pending state and guard result handling | Snapshot limitation is real, but 2.1.2 already recorded notification_pending and guarded durable recording. GUI consumption/close run on the UI thread; arbitrary ThreadPool callbacks do not directly run ConsumeResult. Pending now explicitly means completion callback pending at record time, not UI message consumption. It is set before atomic result publication. Future callback errors cannot be known at an earlier journal sample. |
| P4: a small rollback forces another full validation | True and intentional. No input/lifecycle signal does not establish that another process left the target unchanged. Only a known pre-commit no-input early sample can resume waiting, and it revalidates before eventual dispatch. There is no retry of a possibly sent action. |
| P5: gradual clock slew can exceed the 100 ms cumulative budget over a long wait | Valid policy cost, already disclosed; a hypothetical slew rate is not evidence of the owner's actual machine state. The budget is retained rather than silently relaxed with elapsed time. New schedules are capped at 24 hours; operators should arm near use. Far pauses are bounded at 100 ms, near pauses at 50 ms, preserving the 250 ms stall rule. Power behavior is explicit before arming. |
| P6: baseline .cs files make every IDE immediately report duplicates | Overstated. There is no SDK project that implicitly compiles the whole export; the supported launcher enumerates exactly three production files. A recursive external analyzer/project could include both. Historical files now use .cs.snapshot and compile only after test-only staging. This is packaging hygiene, not a reproduced failure of the supported build. |

R1 says it had not inspected the inner C# files. Its proposed line-level changes and causal explanations therefore cannot be accepted as independently source-verified findings. The new outer bundle includes a flat exact project copy to remove that access obstacle.

## Additional issue found during real fixture verification

The first 2.1.3 physical UI workflow successfully delivered its one owned-button click, then failed the power_changed reason assertion. It sent zero packets for that cancelled schedule. Inspection and a deterministic reproduction showed a race: after the loop's initial cancellation read, lifecycle cancellation and health-generation invalidation could occur together; the health rejection overwrote the already accepted cancellation reason.

Completion now atomically publishes a terminal state/result pair and preserves a cancellation reason whose CAS won before completion for a no-input outcome. It never rewrites a committed/native result as cancelled. The failing physical receipt and exact intermediate source/test snapshots are preserved and labelled separately. A new boundary regression fails before this fix and passes afterward. Existing competing-canceller, accepted-cancellation/no-input, callback and disposal tests still pass.

## Evidence scope and release checks

Eight baseline/fixed groups, the boundary contracts, old fault/deadline/refinement/review/rereview suites, launcher/build/path/platform checks and owned native/UI fixtures are distinct evidence. Simulated boundary safety states test control flow; real owned geometry checks test selected Win32 behavior; injected desktop names are not a real desktop switch. Source hashes bind each receipt to its actual input files. Failed or intermediate runs are retained rather than relabeled as final passes.

The final source passed 21 physical fixture trials (three success, three of each six negative scenarios) and all 42 full UI checks with exactly one owned-button click. The three native-boundary lateness samples were 12.3554, 1.6822 and 1.4404 ms; target MouseDown lateness was 27.1629, 19.9152 and 8.7672 ms. Full-capture guard durations were 2.0266, 1.2011 and 1.0786 ms. These are measurements of this workload, not a speedup claim. Full-precision ISO timestamps, source bindings and counts are in the release receipt and VALIDATION_SUMMARY.

Manual render inspection confirms one layout's readability, not a pixel/DPI proof. Remaining untested cases include every display/DPI/edge combination, 32-bit delivery, actual sleep/lock/hotplug, elevated targets, actual native partial returns, remote sessions and long-wait stressed tails. No worst-case, percentile, 1 ms target receipt or financial-order outcome follows from these tests.

The outer delivery includes the sealed project ZIP, validation/check/hash sidecars, sanitized fresh reports and a flat project/ copy byte-identical to the inner ZIP. Baseline sources are .cs.snapshot files. Historical receipts are explicitly labelled; private review attachments/account journals remain excluded. Unsigned manifests detect internal inconsistency, not publisher identity. The final receipt distinguishes pre-sanitization hashes of excluded originals from hashes that recipients can recompute on delivered bytes.

## Primary API references

- [WindowFromPoint](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-windowfrompoint) and [layered windows](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features): hit testing and visual/input behavior are separate from retaining an unobscured application target after restoration.
- [FileStream.Flush](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=netframework-4.8.1): buffered I/O/flush failure is not an atomic transaction guarantee.
- [SetThreadExecutionState](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate): system/display requests are thread-scoped, with explicit restoration; this does not prevent user-requested sleep.
- [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput): packet count is not destination processing or broker/exchange acceptance.
